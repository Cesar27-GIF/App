Logica del semaforo conductual

Flujo completo desde el registro de una incidencia hasta la notificacion al padre de familia.

≥ 80 pts
VERDE
Sin intervencion requerida
40 – 79 pts
NARANJA
Seguimiento preventivo
< 40 pts
ROJO
Intervencion urgente

Flujo de eventos en la base de datos

1
Docente / orientador / directivo registra una incidencia

INSERT INTO incidencias (alumno_id, registrado_por, categoria_id, impacto_puntos…)
El constraint CHK_incidencia_registrador (v2, OWASP A01) verifica en BD — no en la app — que el registrado_por tenga un rol autorizado. Un padre o alumno no puede insertar aunque evada la capa de aplicacion.

2
Trigger TR_incidencias_actualiza_puntos (automatico)

Recalcula alumnos.puntos_totales haciendo SUM(impacto_puntos) de todas las incidencias del alumno. Recalculo completo, no suma/resta incremental, para evitar deriva acumulada ante futuros UPDATE o DELETE de incidencias anteriores.

3
nivel_semaforo se recalcula como columna PERSISTED

SQL Server recalcula automaticamente la columna calculada al cambiar puntos_totales:
CASE WHEN puntos_totales ≥ 80 THEN 'verde' WHEN puntos_totales ≥ 40 THEN 'naranja' ELSE 'rojo' END

4
Trigger TR_historial_semaforo_auto (solo si el color cambio)

Compara nivel_semaforo de inserted vs deleted. Si difieren, inserta en historial_semaforo con el color anterior, el nuevo y causado_por = NULL (indicando origen automatico). Sin ruido para cambios de puntos que no cruzaron umbral.

5
El backend genera notificaciones a padres y orientadores

La API consulta padres_alumnos WHERE notificaciones_activas = 1 e inserta en notificaciones con el canal correspondiente. El envio push/email ocurre fuera de la BD — la base solo persiste el registro.

6
Trigger TR_audit_incidencias registra la operacion en audit_log

Corre en el mismo batch que el paso 1 (AFTER INSERT). Serializa la fila en JSON y la persiste en audit_log con sistema_origen = 'TRIGGER'. El usuario_id lo puede inyectar la API en la sesion de conexion si se implementa SET CONTEXT_INFO.

Roles y permisos

Matriz de acceso a operaciones criticas. El enforcement primario es la API; las correcciones v2 agregan enforcement secundario en la BD para las operaciones mas sensibles.

OWASP A01:2025 (Broken Access Control): los controles solo en la capa de aplicacion son insuficientes. Un bug, una migracion manual o acceso directo a la BD evadiran el control. La v2 implementa CHK_incidencia_registrador como primera linea de defensa en BD. Se recomienda extender el mismo patron a seguimientos (solo orientadores y directivos).

Correcciones aplicadas en v2

11 cambios organizados por categoria: seguridad (OWASP / LFPDPPP) y eficiencia.

Seguridad

SEC-1

Esquema de contrasenas seguras OWASP A04 A07

La tabla usuarios no tenia columna de credenciales. Se agrega password_hash NVARCHAR(255) NOT NULL DEFAULT ''. El DEFAULT vacio fuerza un reset en el primer login. El backend debe usar Argon2id (preferido) o bcrypt con work factor ≥ 12, generando un Salt aleatorio de 16 bytes por usuario. Nunca almacenar texto plano. Se agregan tambien intentos_fallidos, bloqueado_hasta y ultimo_login.

SEC-2

Tabla audit_log y triggers de trazabilidad A09

Sin auditoria no hay trazabilidad institucional. Se crea audit_log con valor_anterior y valor_nuevo serializados como JSON. Tres triggers (uno por tabla critica: incidencias, alumnos, historial_semaforo) la alimentan automaticamente ante INSERT/UPDATE/DELETE. Cumple requerimientos de compliance de organismos educativos bajo supervision de la SEP y la LFPDPPP.

SEC-3

Constraint de control de acceso en incidencias OWASP A01

El DDL v1 indicaba en un comentario que la validacion del rol se haria en backend o RLS, pero no habia ninguna salvaguarda en la BD. Se crea la funcion escalar determinista fn_es_registrador_valido con WITH SCHEMABINDING y el constraint CHK_incidencia_registrador. Bloquea inserciones de roles padre y alumno incluso si la API es eludida.

SEC-4

Cifrado de datos personales (LFPDPPP Arts. 3, 9, 19 y 48)

correo_personal y telefono en alumnos son datos personales bajo la LFPDPPP. Su exposicion puede generar sanciones del INAI (Art. 64). Se implementa cifrado simetrico nativo: Database Master Key + certificado autofirmado + Symmetric Key AES-256. Se agregan columnas correo_personal_enc y telefono_enc de tipo VARBINARY(500). Los datos existentes se migran con ENCRYPTBYKEY. Las columnas de texto plano se eliminan tras validar en entorno de pruebas.

SEC-5

Tabla sai_sync_log para trazabilidad de sincronizaciones Integridad

El campo alumnos.sai_sync_at solo guardaba el ultimo timestamp. Una sincronizacion parcial era indistinguible de una exitosa. La nueva tabla registra cada sincronizacion con estado (iniciada / completada / fallida / parcial) y conteo de registros procesados correctamente vs con error.

SEC-6

Tabla refresh_tokens para control de sesiones OWASP A07

Sin tabla de sesiones no es posible invalidar un token robado, forzar logout global ni detectar dispositivos sospechosos. La tabla refresh_tokens almacena el hash del token (nunca el token en texto plano), la informacion del dispositivo, la IP, la fecha de expiracion y el flag revocado. Al revocar, marcar revocado = 1 en la misma transaccion que emite el nuevo token para prevenir replay attacks.

Eficiencia y rendimiento

EFF-1

Trigger TR_incidencias_actualiza_puntos

puntos_totales era un campo normal que la API debia actualizar manualmente. Cualquier ruta que omitiera ese paso dejaba nivel_semaforo desincronizado sin advertencia. El trigger recalcula con SUM completo (no incremento) para evitar deriva acumulada ante UPDATE o DELETE de incidencias previas.

EFF-2

Indices NONCLUSTERED en FK sin indice

SQL Server no crea indices automaticamente en columnas FK. Las siguientes FK carecian de indice en la v1: carreras(plantel_id), grupos(plantel_id), grupos(periodo_id), materias(grupo_id), materias(docente_id), incidencias(registrado_por), seguimientos(alumno_id), seguimientos(orientador_id), padres_alumnos(alumno_id). Cada una generaba full scans en sus respectivos JOINs.

EFF-3

Correccion NEWID() vs NEWSEQUENTIALID() en el seed

La tabla define DEFAULT NEWSEQUENTIALID() para que el B-Tree inserte hojas siempre al final, evitando page splits. El seed v1 usaba NEWID() (UUID aleatorio) al declarar las variables, fragmentando el indice clustered desde la primera ejecucion. La solucion es omitir el id en el INSERT y capturar el valor generado con OUTPUT INSERTED.id si se necesita referenciar en el mismo script.

EFF-4

Trigger TR_historial_semaforo_auto

El historial solo se registraba cuando la API lo recordaba. Rutas de actualizacion directa de puntos omitian el paso, dejando brechas en la bitacora conductual. El trigger garantiza el registro automatico y solo cuando el color efectivamente cambia, evitando ruido en la tabla.

EFF-5

Indice IX_avisos_dirigido_activo con INCLUDE

La pantalla principal del alumno ejecuta en cada carga la query WHERE plantel_id = X AND activo = 1 AND dirigido_a IN ('todos', 'semaforo_naranja'). Sin indice era un full scan. El nuevo indice sobre (plantel_id, dirigido_a, activo) con INCLUDE(titulo, fecha_evento, descripcion) convierte la consulta en una index-only scan al no necesitar acceder a la tabla base.

Dashboard del alumno

Estado conductual actual

Cubre el bloque "Estado Conductual" del prototipo. Indice clustered por PK en alumnos.

SELECT a.puntos_totales, a.nivel_semaforo, a.matricula,
       u.nombre, u.apellido, g.nombre AS grupo,
       c.nombre AS carrera
FROM   alumnos a
INNER JOIN usuarios u ON a.usuario_id = u.id
INNER JOIN grupos   g ON a.grupo_id   = g.id
INNER JOIN carreras c ON g.carrera_id = c.id
WHERE  a.usuario_id = @usuario_id;

Actividad reciente (ultimas 10 incidencias)

Usa IX_incidencias_alumno (alumno_id, created_at DESC). Sin este indice era un full scan con ORDER BY.

SELECT TOP 10
    i.created_at,
    ci.nombre        AS categoria,
    ci.color_semaforo,
    i.descripcion,
    i.impacto_puntos
FROM   incidencias i
INNER JOIN categorias_incidencia ci ON i.categoria_id = ci.id
WHERE  i.alumno_id = @alumno_id
ORDER BY i.created_at DESC;

Aviso proximo segmentado por semaforo

Cubre el bloque "Aviso Proximo". Usa IX_avisos_dirigido_activo (index-only scan en v2).

-- @color_alumno = nivel_semaforo del alumno autenticado
SELECT TOP 1 titulo, descripcion, fecha_evento
FROM   avisos
WHERE  plantel_id = @plantel_id
  AND  activo     = 1
  AND  dirigido_a IN ('todos', 'semaforo_' + @color_alumno)
ORDER BY fecha_evento ASC;

Dashboard de orientacion

Alumnos en semaforo rojo del periodo activo

nivel_semaforo es columna PERSISTED; SQL Server la puede filtrar directamente sin recalcular.

SELECT a.id, u.nombre, u.apellido, a.matricula,
       a.puntos_totales, a.nivel_semaforo,
       g.nombre AS grupo
FROM   alumnos a
INNER JOIN usuarios u ON a.usuario_id = u.id
INNER JOIN grupos   g ON a.grupo_id   = g.id
WHERE  g.periodo_id  = @periodo_activo_id
  AND  a.nivel_semaforo = 'rojo'
ORDER BY a.puntos_totales ASC;

Historial de semaforo de un alumno en el periodo

Usa IX_historial_alumno. La desnormalizacion de periodo_id evita JOINs adicionales en una tabla que puede tener cientos de miles de filas.

SELECT color_anterior, color_nuevo,
       motivo, causado_por, created_at
FROM   historial_semaforo
WHERE  alumno_id  = @alumno_id
  AND  periodo_id = @periodo_id
ORDER BY created_at DESC;

Reportes para directivos

Distribucion de semaforo por grupo

Agregacion sobre nivel_semaforo (columna PERSISTED). No requiere subconsultas ni recalculos.

SELECT
    g.nombre AS grupo,
    COUNT(CASE WHEN a.nivel_semaforo = 'verde'   THEN 1 END) AS verde,
    COUNT(CASE WHEN a.nivel_semaforo = 'naranja' THEN 1 END) AS naranja,
    COUNT(CASE WHEN a.nivel_semaforo = 'rojo'    THEN 1 END) AS rojo,
    COUNT(*)                                                  AS total
FROM   grupos g
INNER JOIN alumnos a ON a.grupo_id = g.id
WHERE  g.periodo_id = @periodo_activo_id
  AND  g.plantel_id = @plantel_id
GROUP BY g.id, g.nombre
ORDER BY g.nombre;

Leer dato personal cifrado (correo o telefono)

Requiere abrir la Symmetric Key en la sesion. El backend debe cerrarla inmediatamente despues de leer.

OPEN SYMMETRIC KEY SYMKEY_EduTrack_DatosPers
    DECRYPTION BY CERTIFICATE CERT_EduTrack_DatosPers;

SELECT
    a.id,
    CAST(DECRYPTBYKEY(a.correo_personal_enc) AS NVARCHAR(200)) AS correo_personal,
    CAST(DECRYPTBYKEY(a.telefono_enc)        AS NVARCHAR(20))  AS telefono
FROM   alumnos a
WHERE  a.id = @alumno_id;

CLOSE SYMMETRIC KEY SYMKEY_EduTrack_DatosPers;
Todas las queries anteriores estan cubiertas por al menos un indice definido en el DDL v2. No hay full scans en las rutas criticas del prototipo.
